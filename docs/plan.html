Ringer on the BEAM

A plan to rebuild Ringer as an Elixir/OTP application with a LiveView Ringside. The goal is to replace Ringer's machinery with the things OTP already does, not to translate 11,233 lines of Python line by line.

First: a separate repo that tracks upstream

origin is NateBJones-Projects/ringer. 97 of the 107 commits are Jonathan Edwards's and none are yours. [update] auto fast-forwards this checkout onto upstream main whenever a command runs. Decided 2026-09-25: the Elixir version lives in a fork or a new repo that keeps tracking upstream. The Python stays as the reference implementation and test oracle. Tracking upstream below recommends which of the two and how the tracking works. Any Python checkout you keep using alongside it needs auto = false, or upstream will move the oracle under your tests.

What you give up: today's install is git clone && ./ringer.py on stock Python 3.12, standard library only (psycopg is optional). A BEAM app needs either a local Erlang/Elixir toolchain or a bundled binary. That cost falls on every future user, not just on you.

Tracking upstream

Upstream is still moving. In September, #59 added 99 lines to ringer.py (warnings about worker commands) and #101 changed 9 (exact bytes in the demo output), and about 600 lines landed across 9 files between 30 August and 15 September. A port that doesn't track upstream starts falling behind as soon as it forks.

Recommendation: a new repo that pins upstream, not a GitHub fork

Why not a fork: a fork's history is the Python tree. Every upstream merge would touch ringer.py, tests/ and dashboard/, which the port has deleted or replaced, so each sync means conflicts that tell you nothing. Git has no way to express "the same behaviour, now in another language". GitHub also keeps a fork of a public repo public, and points its pull requests at upstream by default.

Instead: a new repo (working name ringer-ex) with upstream as a read-only git submodule at vendor/ringer-py, pinned to a SHA. The pin is the whole relationship: moving it is a deliberate, reviewable one-line commit, and the Python oracle the tests run against is exactly that SHA.

What flows through the pin

Some of upstream is language-agnostic. That part is consumed from the pin, not copied, so upstream improvements arrive with a bump and no porting work:

The bump loop

  • Two oracle checks, not one. The suite is first run against the Python at the new SHA. If upstream's own behaviour moved, the cases' recorded expectations change in the same bump commit. Then the Elixir runs against those expectations. The difference is the porting work.
  • The suite only sees what it exercises. A new upstream feature with no conformance case would pass silently. So the job also diffs upstream's argparse definitions (build_parser, ringer.py:10866), the manifest fields in TaskSpec and the tests/ file list between the old and new SHA, and files anything new as "needs a case".
  • A divergence ledger. Some differences are intended: the retired per-run dashboard, daemon semantics, a new circuit breaker. Record each one in DIVERGENCES.toml with the conformance case it affects, the reason and the date. The suite reads it and treats those cases as expected diffs. Without the ledger, every deliberate difference would look like drift forever.
  • Ringer ports its own changes. A drift item is a swarm-shaped task: the spec is the upstream diff plus the failing case, and the check is that the case passes. That is Ringer's own model of verifying by execution, so porting runs as a manifest, with the Elixir Ringer as soon as it can host runs.
  • Landing. A green bump fast-forwards onto trunk with no PR, the same as your other autonomous work. Tags still gate releases, so landing a bump ships nothing.

deferred When to stop tracking: if the divergence ledger grows past the conformance cases that still match, or upstream goes quiet for a quarter, freeze the pin and say so in the README. The port then stands alone, and the ledger records exactly where it split.

What the Python does today

Every ringer run is its own OS process. Nothing is shared in memory, so runs coordinate through the filesystem. Each run rewrites its whole state JSON about once a second from a background thread, walking ps each time to count worker sub-processes. active-runs.json is a registry held together by PID liveness probes. Ringside is a separate process that polls /api/runs every second, and the Tauri HUD, the Claude skill and the nudge hook all read those files directly. File locks and mkstemp-plus-rename exist to stop concurrent writers from colliding: the fix for the "shutdown-test flake" (#84) was exactly that.

Almost all of that coordination code exists because the runs share no memory. On the BEAM they would share a node, so most of it can go.

The shape decision: one long-lived node

Recommendation: a daemon hosts runs, and the CLI is a thin client

A single ringer node owns every run. ringer run manifest.json connects to it over a Unix socket (mode 0600), submits the manifest, streams progress events back and exits 0 only if every task passed, the same exit-code contract as today. If no daemon is running, the CLI starts one, as ensure_hud_running already does for the HUD (ringer.py:10800).

Why: the payoff only arrives when runs share a node. Registry replaces active-runs.json and the PID probes. Phoenix.PubSub replaces the 1-second file polling, so LiveView gets pushed each state change as it happens. A single writer process replaces the file locks. One-BEAM-per-run keeps all the file plumbing and gains little beyond typed processes.

Cost: the daemon becomes one more thing that can be down, stale, or running old code. Today a run lives and dies with the terminal that launched it; under a daemon a crash takes every in-flight run with it. The mitigations are supervision, a small hosted surface, and the standalone mode below.

The daemon must never resolve anything against its own environment

Today, several inputs are resolved relative to whoever typed the command: identity (--identity, then FLEET_IDENTITY/RINGER_IDENTITY, then a .fleet-agent file found by walking up from the cwd, ringer.py:9470-9510), engine binaries (shutil.which("codex") against the caller's PATH, which under mise differs from shell to shell), and relative workdir, repo, expect_files and ask --source paths. Under a daemon those would silently resolve against the daemon's environment instead. So the CLI resolves identity and every path to an absolute value, captures the resolved engine binary paths (or its PATH), and sends all of it with the manifest. Standalone mode can't catch this class of bug, so the phase 3 conformance run has to launch the CLI from a different cwd and PATH than the daemon's.

Keep the run subtree host-agnostic. The same Run supervisor can start under the daemon or inside a CLI VM started with --standalone. That gives CI and tests a daemon-free path, and it lets phase 2 ship at full parity before the daemon exists.

The security seam

The org-brain card provisioning-privilege-belongs-behind-an-os-process-boundary applies directly. The daemon runs arbitrary shell check commands and unsandboxed full_access workers, and under this plan it also serves HTTP on localhost. A GenServer boundary is not a security boundary. Any page that can make that endpoint start a run has remote code execution.

  • Runs start only over the 0600 Unix socket. No HTTP route accepts a manifest, a command or a path.
  • UI actions, when they arrive, pass a key rather than a payload: "cancel run <id>" is fine, "rerun with this spec" is not.
  • Bind to 127.0.0.1, keep check_origin strict and require a per-install token for socket upgrades. This handles DNS rebinding against localhost.
  • No distributed Erlang between the CLI and the daemon. A shared cookie lets either side :rpc the other.
  • deferred Splitting the executor into its own OS process. Trigger to revisit: any feature that lets something other than you reach the endpoint (remote viewing, a LAN bind, multiple users). The executor would need: its own socket, manifests looked up by run key, and concurrency ceilings enforced on its side.

What the BEAM makes newly cheap (after parity)

  • Per-engine circuit breaker. As of the 2026-08-07 review, your last recorded demo run (2026-07-22) burned both attempts on all three tasks against a Codex usage-limit error. A breaker process per engine that trips on the known limit text would pause that engine's queue instead of spending retries.
  • Global per-engine concurrency. Today max_parallel is per run, so two concurrent swarms can double-book one provider. A daemon-level limiter per engine fixes that.
  • Cancel from the UI by run key, through the seam rules above.
  • Live log streaming. erlexec delivers stdout as messages, so the log tail becomes a stream instead of re-reading the last 40 lines every second.

Testing: at the boundary, against both implementations

Don't port the ~267 unittest functions. Build a conformance suite in ExUnit that drives the CLI through System.cmd with a fake engine and asserts only on the contracts table: exit code, stdout summary, runs.jsonl rows, state JSON, deliverables and worktree effects. Point it at the Python first to characterise the current behaviour, then at the Elixir. Behaviour both pass is parity; behaviour that differs is either a deliberate, logged change or a bug.

  • The fake worker must be a shell script. engines/mock_worker.py would make the Elixir suite need Python.
  • LiveView tests exercise full flows: open Ringside, start a run over the socket, and watch rows change state. Tests that mount a LiveView with hand-built assigns don't count.
  • Unit tests only where the logic is a real algorithm reachable only from inside: lint heuristics (check_cannot_fail and friends) and ask's chunk scoring. StreamData fits both.
  • templates/*/checks/*.py are user-side check scripts run by sh. They are out of scope and stay Python.

Phases

0

Process-control spike

Prove erlexec (MuonTrap as the fallback) against the four behaviours Ringer depends on.

Done when: an ExUnit test shows (1) kill_timeout kills a worker and its grandchildren; (2) kill -9 of the BEAM leaves no worker alive; (3) stdout arrives in chunks while the worker runs; (4) exit status and timeout can be told apart. Passes on macOS and Linux. If this fails, nothing downstream ships.

1

Repo, pin, harness + pure core

Create ringer-ex with the vendor/ringer-py submodule, the conformance harness, DIVERGENCES.toml and the scheduled bump job. Get the harness green against the pinned Python. Then port the pure modules: manifest and config changesets, lint, the ask context packet, steering profiles, run-ID and identity resolution. ringer lint is the first Elixir command.

Done when: ringer lint output matches the Python byte for byte across every templates/*/manifest.json and your two swarm files, and one bump-job run against current upstream lands green or files drift items.

2

Standalone run

Run subtree, Task.Lifecycle, Verifier, worktrees, deliverable harvest, EvalLog, StateMirror and the active-runs.json projection, hosted in the CLI VM. Also --baseline, --dry-run, demo, ask end to end, steering observation writes, and install-agent/uninstall-agent.

Done when: the conformance suite passes identically on both implementations, and the Python Ringside and Tauri HUD show an Elixir run correctly (proving the projection honours the contract).

3

Daemon + LiveView Ringside

Control socket, auto-start, Registry, PubSub, and the Ringside, run and library pages as LiveViews. Final reports render from the same HEEx components.

Done when: two swarms started from two terminals appear on one Ringside with no polling in the network tab, and a full-flow LiveView test covers start → row changes → final report link.

4

Read side

models, catalog, db and the scoreboard page, on ecto_sqlite3 with the Projector.

Done when: models output matches the Python for your real runs.jsonl.

5

Ship: release, update, HUD

mix release, with Burrito considered for a single binary. Self-update becomes: fetch a release, wait until the Registry shows no live runs, then restart (the Python's hud_should_restart is the precedent). hud and self-update become thin commands against the daemon. erlexec's exec-port is a compiled C++ program, which affects any single-binary build: it has to be built per target OS and architecture. Point the Tauri webview at the LiveView URL and drop hud.js's file scanning, or retire Tauri.

Done when: a fresh machine goes from download to a passing demo in one documented command, and an update applied while a run is live waits for the run to finish.

Your calls

  • Daemon or standalone as the default for ringer run (recommended: daemon, with --standalone for CI).
  • When the client disconnects: today Ctrl-C cancels the run and kills its workers (the CancelledError path in RingerRunner.run), and an agent may rely on that to abort a swarm. Recommended: a disconnect cancels the run, unless it was started with --detach.
  • Tauri: keep it as a webview onto LiveView, or retire it (recommended: webview; it keeps the always-on-top window at almost no cost).
  • Distribution: require an Elixir toolchain, or ship a bundled binary.
  • Where drift gets reported: GitHub issues on the new repo, or Linear. The bump job needs one place to file what it finds.

Not verified

  • unverified erlexec's behaviour when the BEAM itself is SIGKILLed. The docs cover kill_group on the owning Erlang process exiting, not the VM dying. Phase 0 test (2) exists for this.
  • unverified Burrito: Context7 had no entry for the Elixir project (only an unrelated Terraform operator of the same name). Check the hex docs before relying on it.
  • unverified Which Elixir TOML parser is maintained today, and whether Oban's SQLite engine suits a single-node daemon.
  • No library versions are pinned here on purpose. Pin them from hex when phase 0 starts.
